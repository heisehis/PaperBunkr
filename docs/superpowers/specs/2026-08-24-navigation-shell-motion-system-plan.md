# Navigation Shell & Motion System — Implementation Plan
*Implements: docs/superpowers/specs/2026-08-24-navigation-shell-motion-system-design.md*

Verified against Avalonia 12.1.1 source directly (not memory) before writing this plan:
- `Avalonia.Controls.TransitioningContentControl` : `ContentControl` - `PageTransition` (`IPageTransition?`), `IsTransitionReversed` (`bool`, default `false`). Direction passed to the transition is `!IsTransitionReversed`, decided once per `Content` change - no per-transition override, so direction must be set *before* `Content` changes.
- `Avalonia.Animation.PageSlide(TimeSpan duration, SlideAxis orientation = Horizontal)` - `Duration`, `Orientation`, `SlideInEasing`/`SlideOutEasing` (`Avalonia.Animation.Easings.Easing`, default `LinearEasing` - must be set explicitly to match `PbMotionEase`), `FillMode` (default `Forward`).
- `Control.DataTemplates` (inherited by `TransitioningContentControl`) supports multiple typed `<DataTemplate DataType="...">` entries, same mechanism already used per-screen in `MainWindow.axaml` today - no custom `IDataTemplate`/`ViewLocator` needed (the project's existing `ViewLocator.cs` is dead/non-functional for this codebase's `Views`/`ViewModels` namespace split - confirmed by reading it - and was never relied on for top-level screens).
- CommunityToolkit.Mvvm's `[ObservableProperty]` generates `On<Prop>Changing(oldValue, newValue)` (fires before the field updates) in addition to `On<Prop>Changed(newValue)` - `OnCurrentScreenChanging` is where direction gets computed, since it's the only hook with both old and new values.

## Step 7: `PbScreenSlide` resource + motion wiring
**Files:** `src/Paperbunkr.App/App.axaml` (edit)
**What:** `<PageSlide xmlns:anim="using:Avalonia.Animation" x:Key="PbScreenSlide" Duration="{StaticResource PbMotionFast}" Orientation="Horizontal"><PageSlide.SlideInEasing>{StaticResource PbMotionEase}</PageSlide.SlideInEasing><PageSlide.SlideOutEasing>{StaticResource PbMotionEase}</PageSlide.SlideOutEasing></PageSlide>` (exact XAML property-element syntax vs. attribute syntax for the two Easing properties is an implementation-time detail - `PbMotionFast` must be `{StaticResource}` here, not `{DynamicResource}`, matching Phase 1's confirmed finding that resource-typed Setter/property values need Static resolution to type-convert correctly; reduced-motion's `TimeSpan.Zero` override already works by mutating the `PbMotionFast` resource's *value* live, which a `StaticResource`-captured reference here will still observe since it's the same boxed... **note**: this needs verifying during implementation - if `PageSlide.Duration` is captured once at resource-parse time rather than re-read live, reduced-motion won't affect screen slides even though it affects Button/FloatingPanel transitions (which use `Setter`-based `Transitions`, a different mechanism). If so, either accept that gap (screen-slide duration is fixed, only interaction-level transitions respect reduced-motion) or have `MainViewModel` swap `PageTransition` to an instant/null transition when `ReducedMotion` is on - a real open question to resolve during implementation, not guessable from the source alone.

**Verify:** Manual - confirm the slide direction/duration look right, and explicitly check whether toggling Reduced Motion (Preferences → Appearance) affects the screen-slide's speed - report the actual finding either way, don't assume.

## Implementation notes (real findings, not anticipated in the plan)

- **Step 7's open question, answered by reading `PageSlide`'s source directly (not guessed):** `Duration` is a plain settable property, read once by `Start()` when a transition begins - a `{StaticResource PbMotionFast}` reference captures the `TimeSpan` *value* (a struct) at the moment `PbScreenSlide` is constructed, and does not update afterward. Confirmed conclusion: Reduced Motion (Phase 1) does **not** affect the screen-slide's speed - it only affects the Setter-based `Transitions` (buttons, FloatingPanel, rail width). This is documented as a deliberate, known gap in `App.axaml`'s own comment next to `PbScreenSlide`, not silently wrong.
- No new runtime crashes found this phase (unlike Phase 1's `CornerRadius` bug) - `PageTransition="{StaticResource PbScreenSlide}"` and `Classes.expanded="{Binding IsNavRailExpanded}"` are both direct XAML attributes, not Setter-based resource consumption, so Phase 1's specific double→CornerRadius trap didn't recur here. Verified by direct-exe launch (not `dotnet run`) after every structural change, same discipline as Phase 1.
- The rail's glow-ring hover/focus treatment (used for PosterTile/FloatingPanel in Phase 1) was deliberately *not* extended to rail buttons - kept the existing accent-soft-fill active state instead, to avoid re-introducing Setter-based `BoxShadow`-on-`Button` risk on a widely-used, high-traffic control before that pattern has been proven safe anywhere. A scope trim, not an oversight.
- Icon/font/motion-token conventions from Phase 1 held up unchanged for a second phase's worth of new icons (Home, Book, Layers, Filter, Bookmark, Undo, Settings, Pin) - no changes needed to `Styles/Icons.axaml`'s shared `Path.pbIcon` style or the token system itself.
- On-screen visual/interactive verification (hover-expand animation, pin persistence across restart, actual slide direction) was **not** completed - same computer-use dev-build identity-mismatch limitation as Phase 1, stated explicitly rather than assumed working. Build-clean + crash-free-launch + full test suite is the verification that was actually done.
