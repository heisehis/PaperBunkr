## Step 1: Strip classification + cache key types
**Files:** `src/Paperbunkr.App/Services/Reader/ReaderCacheTypes.cs` (edit), `src/Paperbunkr.App/Services/Reader/ReaderImagePipeline.cs` (edit)
**What:**
- Add `public readonly record struct StripBandId(string Container, long ContainerStamp, int PageIndex, int Band);` to `ReaderCacheTypes.cs`, parallel to `PageId` (design §4.1).
- Add `private const double StripAspectThreshold = 3.0;` and `private const int BandHeight = 4096;` to `ReaderImagePipeline`.
- Add a private `PeekPageSize(int pageIndex)` helper: calls `ReadRawBytes(pageIndex)`, opens `SkiaSharp.SKCodec.Create` on the bytes, reads `.Info.Width`/`.Info.Height`, returns `PixelSize?` (`null` on any failure — corrupt bytes, unsupported format, codec creation failure). No `GetPixels`/scanline call. Add a private `IsStrip(int pageIndex)` that calls `PeekPageSize` and tests `height / (double)width > StripAspectThreshold`, caching the strip/non-strip verdict per page index (a `Dictionary<int, bool>`, guarded by `_sync`) so repeated calls don't re-peek.
**Depends on:** none
**Verify:** new unit tests in a new `src/Paperbunkr.App.Tests/Reader/ReaderImagePipelineStripTests.cs` — `PeekPageSize` returns correct width/height for a real fixture without a decode side effect (assert via a fixture whose pixel data is truncated/corrupt past the header — a full decode throws, the peek doesn't); `IsStrip` true for an 800×6000-shaped page, false for a normal 660×1010-shaped one.

## Step 3: `StripDecodeSession` — chunked, forward-only scanline decode
**Files:** `src/Paperbunkr.App/Services/Reader/StripDecodeSession.cs` (new)
**What:** Internal sealed class, one instance per strip currently in reach of the window (design §4.1):
- Constructor takes the raw bytes (already read via `ReadRawBytes`) and opens `SKCodec.Create(SKData)`; exposes `int NextUnreadRow { get; private set; }` (starts at 0) and the codec's declared `PixelSize`.
- `SKBitmap? ReadBand(int bandStart, int bandHeightRows, Action<Action> withReaderLock)` — asserts `bandStart >= NextUnreadRow` (forward-only; caller's responsibility to reopen a fresh session otherwise, per design §4.1's "backward request" path). Calls `StartScanlineDecode` once (idempotent - track whether already started), then chunks `SkipScanlines`/`GetScanlines` in slices of at most `BandHeight` rows (design rev 4 — the lock-chunking fix), each slice's `SkipScanlines`/`GetScanlines` pair wrapped in the caller-supplied `withReaderLock` callback (so the *caller*, `ReaderImagePipeline`, owns `_readerLock` — this class has no lock of its own, keeping it a plain, independently-testable decode primitive). Updates `NextUnreadRow`. Returns `null` on any codec failure (`SKCodecResult != Success` from `GetScanlines`, or partial rows — matches the file's existing "one bad page doesn't break the rest" tolerance).
- `IDisposable`/`Dispose()` disposes the underlying `SKCodec`.
**Depends on:** none (pure Skia wrapper, no pipeline dependency — testable standalone with a fake `withReaderLock` that just invokes the action directly).
**Verify:** new `src/Paperbunkr.App.Tests/Reader/StripDecodeSessionTests.cs` — sequential band reads on a synthetic tall PNG *and* JPEG (via Step 2's fixture helper, or a raw in-memory encode) match a full-decode's corresponding rows (design §6 "scanline-session band decode test" — both formats, not just one); a same-session out-of-order (backward) `bandStart < NextUnreadRow` request throws/asserts (documents the forward-only contract the pipeline must respect); the lock-chunking behavior — call `ReadBand` with a large `bandHeightRows` spanning many `BandHeight`-sized chunks, assert `withReaderLock` was invoked multiple times (once per chunk), not once for the whole read (design §6 "lock-chunking test," this half of it — the concurrent-access half is Step 5's).

## Step 4: Async page-size peek wired through the pipeline
**Files:** `src/Paperbunkr.App/Services/Reader/ReaderImagePipeline.cs` (edit), `src/Paperbunkr.App/Services/Reader/IReaderPageSource.cs` (edit)
**What:**
- `IReaderPageSource` gains `void RequestPageSize(int pageIndex);` and `event Action<int, PixelSize>? PageSizeAvailable;` (design §4.3).
- `ReaderImagePipeline`: a third request kind alongside whole-page and (Step 5's) band decode on the existing high/low-priority `Channel<int>` + `_window`/`_enqueued` machinery — simplest correct shape: a small `(RequestKind Kind, int PageIndex, int Band)` struct as the channel's element type (replacing the current bare `int`, since bands need the extra field too — see Step 5) with `RequestKind { WholePage, Band, PageSize }`. `ProcessQueuedPage` becomes `ProcessQueuedRequest`, dispatching on `Kind`; the `PageSize` case calls `PeekPageSize` (Step 1) off the background thread and raises `PageSizeAvailable` (never blocks the caller — `RequestPageSize` only enqueues, exactly like `SetVirtualizationWindow`'s existing enqueue-and-return shape).
- `RequestPageSize` is a no-op (doesn't enqueue) if `_knownPageSizes`-equivalent tracking (a new small `Dictionary<int, PixelSize>` cache inside the pipeline, separate from `PageCanvas`'s own `_knownPageSizes` — the pipeline doesn't reach into the view layer) already has this page's size, or if a `PageSize` request for it is already `_enqueued`.
**Depends on:** Step 1 (`PeekPageSize`)
**Verify:** new tests in `ReaderImagePipelineStripTests.cs` — `RequestPageSize` returns immediately even while a fake slow/blocked container read is in flight on `_readerLock` from another thread (design §6 "RequestPageSize async test" — use a test double or a deliberately slow `IComicAccessorSession` fake, mirroring `ReaderImagePipelineTests`' existing `OnBeforeBackgroundDecode` gate pattern for controlling timing); `PageSizeAvailable` fires with the correct size once the background request completes; requesting an already-known page size doesn't re-enqueue (assert via the gate/counter pattern already used elsewhere in this test class).

## Step 5: Band decode + cache, integrated into the window/prefetch machinery
**Files:** `src/Paperbunkr.App/Services/Reader/ReaderImagePipeline.cs` (edit), `src/Paperbunkr.App/Services/Reader/IReaderPageSource.cs` (edit)
**What:**
- `IReaderPageSource` gains `Bitmap? TryGetCachedBand(int pageIndex, int band);` and reuses the existing `event Action<int> BackgroundDecodeCompleted;` for a landed band too (design §4.4 — "just re-push on any completion," no payload change needed since `PageCanvas`'s subscriber only cares that *something* changed).
- New `Cache<StripBandId, ReaderBitmap> _bandCache` (byte-bounded, shares the display budget the same way the design's §4.1 describes — "same cache row family, same budget" in spirit; simplest correct implementation is its own `Cache` instance sized as a fraction of `_budget.DisplayBytes`, tune the split during the benchmark step).
- `Dictionary<int, StripDecodeSession> _stripSessions` (guarded by `_sync`), one per strip with at least one band in the eviction range (design §4.1's session lifetime). A new `RequestKind.Band` case in `ProcessQueuedRequest`: resolves or creates the strip's session (fresh — forward from 0 — if none exists or if the requested band's start row is behind `NextUnreadRow`, implementing design §4.1's "backward or far-forward → reopen" path), calls `session.ReadBand(...)` with `_readerLock`-taking chunks (Step 3's `withReaderLock` callback wired to the real lock here), stores the result in `_bandCache`, raises `BackgroundDecodeCompleted(pageIndex)`.
- `SetVirtualizationWindow` and `RecomputeFringe` extended: for any page index in range that `IsStrip` (Step 1) returns true for, enqueue `Band` requests for the bands intersecting `[visibleTop − BandHeight, visibleBottom + BandHeight]` instead of a `WholePage` request for that index; evict `_bandCache` entries (and tear down now-bandless strips' sessions) outside `[visibleTop − 2·BandHeight, visibleBottom + 2·BandHeight]`, mirroring the existing whole-page eviction in both methods. Adaptive fringe: reuse `_forwardFringe`'s existing 2→6 computation, scaled to a 1→3 band range for the band-prefetch case (design §4.2 — `Math.Clamp`/a small mapping function, not a second `_recentDecodeMs` tracker).
- `_window`/`_enqueued` become sets of the new request-kind-aware key (or two parallel sets — whichever keeps `ProcessQueuedRequest`'s existing dequeue-and-check-membership shape intact, since that's the exact mechanism design §4.2 relies on for "stale requests are free to skip," verified already correct for whole pages).
**Depends on:** Step 1 (`IsStrip`), Step 3 (`StripDecodeSession`), Step 4 (request-kind plumbing — this step extends the same struct/dispatch Step 4 introduces).
**Verify:** new tests — a synthetic tall strip's bands decode correctly as the virtualization window advances through it (mirrors `TryGetCachedPage_NullThenPopulated_AfterBackgroundDecode`'s existing shape, for bands); a stale band request (window moved past it before the consumer loop reaches it) is skipped — no decode call made (design §6 "stale band request test," assert via a decode-call counter or the same `OnBeforeBackgroundDecode`-style seam extended to bands); the lock-chunking concurrent-access half of design §6's test — a large reverse-scroll-triggered skip does not starve a concurrent request for a *different* page (instrument via a slow fake session + a second thread's request, assert it isn't blocked for the whole skip duration).

## Step 6: Continuous-mode band-slot rendering
**Files:** `src/Paperbunkr.App/Views/ReaderPageVisualHandler.cs` (edit)
**What:**
- `ContinuousPageEntry` (currently `readonly record struct ContinuousPageEntry(Rect Rect, Bitmap? Bitmap)`) gains a strip variant. Simplest shape consistent with the design's "either a whole-page entry or a StripEntry with band slots" (§4.3): keep `ContinuousPageEntry` as-is for whole pages, add a new `internal readonly record struct StripBandSlot(Rect Rect, Bitmap? Bitmap)` and extend `ReaderContinuousVisualData` to carry `IReadOnlyList<ContinuousPageEntry> Pages` (unchanged) plus a new `IReadOnlyList<(Rect Rect, IReadOnlyList<StripBandSlot> Bands)>`-shaped strip list — or, cleaner, a single discriminated entry: change `ContinuousPageEntry` to `(Rect Rect, Bitmap? Bitmap, IReadOnlyList<StripBandSlot>? Bands)` where `Bands is null` means "ordinary whole-page entry, draw `Bitmap`" and non-null means "strip, draw each band slot, ignore `Bitmap`." Pick whichever keeps `RenderContinuous`'s existing per-page loop shape (it already does `if (entry.Bitmap is null) continue;` — extend that check to also handle the `Bands` case) rather than forking into two parallel render loops.
- `RenderContinuous`'s band-slot draw path computes each band's destination rect from the strip's own top-of-strip display offset via the cumulative-offset formula in design §4.1.2 (`bandTop_display = bandIndex · BandHeight · scale`, not derived from the previous band's already-rounded rect) — draws a gap (skips) for a `null` band bitmap, same as today's whole-page gap handling.
**Depends on:** none directly (pure rendering-data-shape change — can be built and tested against hand-constructed `ReaderContinuousVisualData` instances before Step 7 wires real pipeline data into it).
**Verify:** new tests in `src/Paperbunkr.App.Tests/` (wherever `ReaderPageVisualHandler`'s existing coverage lives, or a new file if none does — check first) or, if that class isn't unit-testable in isolation today (likely, given it's compositor-thread rendering code), a pure-math test against just the rect-computation helper extracted for §4.1.2's formula (design §6 "seam test" — assert adjacent bands' rects share an exact boundary across a range of `BandHeight`/zoom/viewport combinations, mirroring how `SpreadLayoutMathTests` presumably already tests `SplitSpread`'s equivalent no-gap-no-overlap property — find and mirror that test's exact shape).

## Step 7: `PageCanvas` wiring — strip-aware continuous push, size peeks, band-completion re-push
**Files:** `src/Paperbunkr.App/Views/PageCanvas.cs` (edit)
**What:**
- `PushContinuousVisualData`: for each `page` in `layout`, if `decodeService.IsStrip(page.Index)` is true (new `IReaderPageSource` member — thin wrapper the interface exposes, backed by Step 1's pipeline-internal `IsStrip`), build the band-slot list instead of a single `TryGetCachedPage`/`GetPage` call — resolve each visible band via `TryGetCachedBand`, leaving `null` slots for not-yet-decoded bands (same non-blocking-peek philosophy the existing whole-page path already has, per the comment at line ~1916).
- For any page entering the window whose size isn't yet in `_knownPageSizes`, call `decodeService.RequestPageSize(page.Index)` (Step 4) — before building `estimatedSizes`/the layout pass that uses it, so a strip whose size lands mid-frame is picked up on the *next* pass (same "settles into place" pattern `_knownPageSizes` already has for post-decode sizes, now also for pre-decode header sizes).
- Subscribe to the new `PageSizeAvailable` event alongside the existing `BackgroundDecodeCompleted` subscription (same attach/detach/re-arm sites: `OnAttachedToVisualTree`, `OnDetachedFromVisualTree`, the `DecoderProperty` change handler) — handler updates `_knownPageSizes[pageIndex] = size` and calls `RequestContinuousPush()`, mirroring `OnBackgroundDecodeCompleted`'s existing UI-thread-hop-and-repush shape.
**Depends on:** Step 4 (`RequestPageSize`/`PageSizeAvailable`), Step 5 (`TryGetCachedBand`, `IsStrip` on the interface), Step 6 (the `ContinuousPageEntry` shape this step populates).
**Verify:** existing `PageCanvas`-adjacent tests (check `PageCanvasTests.cs` or equivalent for the current continuous-push coverage pattern, mirror it) — a strip page's continuous entry carries band slots, not a single bitmap; a strip's true size is used once `PageSizeAvailable` fires, matching design §6's layout test ("correct total scroll extent... once PageSizeAvailable has fired, even before any band decodes").

## Notes on sequencing

Steps 1–4 are close to independent of each other (1 and 2 fully independent; 3 independent of everything; 4 depends only on 1) and could be built in parallel by different sessions if that were ever useful — here they'll be done in order since one session is doing all of it. Step 5 is the integration point everything else depends on. Steps 6 and 7 could swap order (6 first, as written, means 7's tests have real rendering-data shapes to target) but both depend on 5. Steps 8–9 are cleanup/verification, strictly last.
